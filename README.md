# Цифровая визитка — GraphQL API

Публичный read-only GraphQL API, который отдаёт одну деловую визитку: профиль, навыки, опыт работы и проекты.
Данные хранятся в PostgreSQL и синхронизируются из кода при каждом старте.
Точка входа — **Apollo Sandbox**: корень сервиса перенаправляет в него, и запрос визитки уже подставлен.
Мутаций нет, API только читает данные.

## Стек

| Технология                                                | Назначение в проекте                                                       |
| --------------------------------------------------------- | -------------------------------------------------------------------------- |
| TypeScript                                                | строгий режим, ESM, `noUncheckedIndexedAccess`                             |
| Node.js 24                                                | рантайм (версия в `.nvmrc`)                                                |
| NestJS 12                                                 | модули, DI, конфигурация, health checks                                    |
| GraphQL: `@nestjs/graphql` (code first) + Apollo Server 5 | схема из классов, Apollo Sandbox, лимиты запросов                          |
| Prisma ORM 7                                              | миграции и типизированные запросы; вне репозиториев — только ping БД и сид |
| PostgreSQL 18                                             | хранение визитки                                                           |
| DataLoader                                                | пакетная загрузка вложенных полей без N+1                                  |
| Zod                                                       | проверка переменных окружения и данных сида                                |
| Docker / Docker Compose                                   | multi-stage образ и запуск приложения вместе с БД                          |
| Vitest + Testcontainers                                   | unit-тесты и e2e-тесты на настоящем PostgreSQL                             |
| oxlint + Prettier                                         | линтер с type-aware правилами и форматирование                             |

## Быстрый старт (Docker)

Нужны только Docker и Docker Compose.

1. Создайте файл настроек из шаблона:

   ```bash
   cp .env.example .env
   ```

   Копирует шаблон переменных. Для запуска в Docker значения по умолчанию подходят без правок.

2. Соберите образ и запустите приложение с базой:

   ```bash
   docker compose up --build
   ```

   Поднимаются PostgreSQL 18 и API. Миграции и сид выполняются автоматически при каждом старте контейнера (`scripts/entrypoint.sh`), поэтому база готова без ручных шагов.

3. Откройте http://localhost:3000. Корень перенаправит в Apollo Sandbox (`/graphql`). Если порт 3000 занят, задайте `APP_PORT` в `.env`.

4. В Sandbox уже подставлен запрос `BusinessCard`; достаточно нажать Run. Короткий пример запроса — в разделе ниже.

## Локальная разработка (без Docker)

Нужны Node.js 24 (версия в `.nvmrc`) и Docker для базы данных.

1. `cp .env.example .env` — создаёт файл настроек; `DATABASE_URL` указывает на локальный PostgreSQL.
2. `npm ci` — ставит зависимости по `package-lock.json`, генерирует Prisma Client и настраивает git-хуки.
3. `docker compose up -d db` — запускает только PostgreSQL на `127.0.0.1:5432`.
4. `npm run db:setup` — применяет миграции и заполняет базу (`prisma migrate deploy && prisma db seed`).
5. `npm run start:dev` — запускает сервер с перезапуском на http://localhost:3000/graphql и обновляет `schema.gql`.

Проверки:

```bash
npm test               # unit-тесты (Vitest)
npm run test:e2e       # e2e-тесты на Testcontainers, нужен Docker
npm run lint           # oxlint с type-aware правилами
npm run typecheck      # tsc --noEmit
npm run format:check   # Prettier
```

Остальные команды (сборка, миграции, Prisma Studio) — в секции `scripts` файла `package.json`.

## Пример запроса

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Полная схема лежит в [`schema.gql`](schema.gql). Она генерируется из кода, коммитится, а e2e-тест падает, если файл устарел.

## Архитектура

**Слои.** Цепочка для вложенных полей: Resolver → DataLoader → Service → Repository → PostgreSQL. Резолвер описывает API-типы и не знает о базе. Сервис держит бизнес-правила: владельца визитки, фильтрацию по категории, `isCurrent`. Запросы Prisma лежат в репозиториях; исключения — ping БД в health-индикаторе и сид. Поэтому правила тестируются без БД, а смена ORM затрагивает репозитории и эти два места.

**Модули по предметной области.** Каждый раздел визитки — отдельный модуль (`profile`, `skills`, `experience`, `projects`). Дочерние модули добавляют поля в `Profile` собственными резолверами (`@Resolver(() => Profile)`). Модуль профиля от них не зависит, и новый раздел добавляется без правок существующих.

**Контракт отделён от БД.** GraphQL-модели объявлены в `models/`. Enum'ы API сверяются с enum'ами Prisma через `satisfies`, поэтому переименование в БД не может молча изменить API.

**Без N+1.** Вложенные поля грузятся через DataLoader: ключи всех родителей одного тика уходят в БД одним запросом с `IN (…)`. Загрузчики создаются заново на каждый запрос (`LoaderRegistry` в контексте), поэтому кэш не пересекается между запросами. E2e-тест считает SQL-запросы: дерево профиля с 25 элементами в каждом списке выполняется тем же числом запросов, что и с одним (не больше 10).

**Инициализация и сид.** При старте контейнера выполняются `prisma migrate deploy`, затем сид, затем `node dist/main.js`. Данные визитки — код в `profile.data.ts`, который проверяется Zod-схемой до записи. Сид синхронизирует базу по естественным ключам (slug, имя навыка, URL ссылки) в одной транзакции. Повторный запуск безопасен, а id записей стабильны между перезапусками.

**Ошибки.** Намеренные ошибки получают стабильные `extensions.code`: обработчик `graphql/format-error.ts` переводит HTTP-исключения, плагин сложности отдаёт `QUERY_TOO_COMPLEX`, а HTTP-уровень — `TOO_MANY_REQUESTS` и `PAYLOAD_TOO_LARGE`. Всё неожиданное маскируется под `INTERNAL_SERVER_ERROR`: клиент не видит SQL и stack trace, а детали уходят в лог по `x-request-id`.

**Защита публичного эндпоинта.** Лимит сложности операции (`GRAPHQL_MAX_COMPLEXITY`): каждое поле стоит 1, алиасы считаются, поэтому запросы-бомбы отклоняются до выполнения. Тело запроса ограничено 16 КБ: большее получает 413 до разбора GraphQL и проверки сложности. Rate limit по IP (`RATE_LIMIT_MAX` за `RATE_LIMIT_TTL_MS`) работает на HTTP-уровне и считает каждый запрос к `/graphql`, включая introspection и некорректные запросы; при превышении отвечает 429 с `Retry-After`. Health-пробы (`/health/*`) не лимитируются, а результат `/health/ready` кэшируется на 2 секунды. За reverse proxy обязательно задайте `TRUST_PROXY` числом прокси-хопов (в `render.yaml` задано `1`), иначе все посетители выглядят как один IP. Значение проверяется при старте: допустимо только число от 0 до 3, а `true` отвергается, иначе клиент смог бы подделать свой адрес и обойти лимит. Адреса IPv6 считаются по префиксу /64, поэтому сменой адреса внутри своей подсети лимит не обойти. Счётчики лимита живут в памяти процесса: при нескольких репликах каждая пропустит свои `RATE_LIMIT_MAX`, поэтому бесплатный план Render запускает один экземпляр (количество реплик в `render.yaml` не задано). Для нескольких реплик нужен общий store или лимит на уровне прокси.

**Health checks.** `/health/live` не обращается к БД, и её сбой не заставит оркестратор перезапускать здоровый процесс. `/health/ready` проверяет БД; статус базы — только `up` или `down`, при `down` ответ 503.

**Логи и конфигурация.** В production каждое событие пишется одной JSON-строкой: в stdout, а ошибки в stderr. Каждая GraphQL-операция логируется с именем, длительностью и `requestId` (интроспекция Sandbox — на уровне debug). Все переменные приложения описаны в `src/config/env.schema.ts` (Zod): при неверной конфигурации приложение останавливается с понятным сообщением. `NODE_ENV` обязателен и не имеет значения по умолчанию, чтобы забытая переменная не отключила маскирование ошибок. В логах имя операции обрезается до 64 символов.

## Тесты

- **Unit** (`src/**/*.spec.ts`, 110 тестов): DataLoader (батчинг, кэш, изоляция запросов), сервисы, валидация данных сида, маскирование ошибок, конфигурация.
- **e2e** (`test/`, 24 теста): PostgreSQL в Testcontainers, к нему применяются те же миграции и сид, что в production. Проверяются пример запроса, порядок данных, отсутствие N+1, стабильность id, CHECK-ограничения БД, ошибки и лимиты, Sandbox, health checks и актуальность `schema.gql`.

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) прогоняет всё перечисленное на каждый push и pull request, а затем отдельной задачей поднимает стек через Compose с нуля и запрашивает визитку по HTTP.

## Деплой (Render)

Сервис собирает Render из `Dockerfile` по [`render.yaml`](render.yaml): бесплатный план (`free`), health check на `/health/ready`. Миграции и сид выполняются в entrypoint контейнера при каждом старте, отдельного шага деплоя нет.

База — отдельный бесплатный проект Neon (PostgreSQL). Строку подключения задайте в дашборде Render как `DATABASE_URL`: в `render.yaml` переменная помечена `sync: false`, поэтому в репозиторий она не попадает. Строка обязана содержать `sslmode=require`: соединение с Neon идёт через публичную сеть.

| Переменная     | Значение                                       | Зачем                      |
| -------------- | ---------------------------------------------- | -------------------------- |
| `DATABASE_URL` | строка подключения к Neon, с `sslmode=require` | задаётся в дашборде Render |

`NODE_ENV=production` и `TRUST_PROXY=1` уже заданы в `render.yaml`, `PORT` задаёт Render. Остальные переменные имеют значения по умолчанию из `src/config/env.schema.ts`.

**Засыпание.** Бесплатный веб-сервис Render засыпает после 15 минут без трафика; первый запрос после этого получает ответ примерно через минуту.

**Приостановка.** Render предупреждает, что может приостановить бесплатный сервис при необычно большом объёме трафика, например при обращениях к внешней базе данных.

## Как обновить данные визитки

1. Отредактируйте [`src/database/seed/data/profile.data.ts`](src/database/seed/data/profile.data.ts).
2. Пересоберите и перезапустите контейнер: `docker compose up --build`. Данные попадают в образ при сборке, поэтому без `--build` изменения не применятся. Локально достаточно `npm run db:seed`.

Сид синхронизирует базу: изменённые записи обновляются, удалённые из файла удаляются.
