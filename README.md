# Цифровая визитка — GraphQL API

Read-only GraphQL API одной деловой визитки: профиль, навыки, опыт работы и проекты.
Точка входа — Apollo Sandbox, запрос визитки в нём уже подставлен.

**Открыть: https://digital-business-card-nl4y.onrender.com**
Сервис на бесплатном плане и засыпает без трафика — первый запрос может занять до минуты.

## Стек

| Технология                                      | Зачем                                        |
| ----------------------------------------------- | -------------------------------------------- |
| TypeScript, Node.js 26                          | строгий режим, ESM                           |
| NestJS 12                                       | модули, внедрение зависимостей, конфигурация |
| `@nestjs/graphql` (code first), Apollo Server 5 | схема из классов, Sandbox                    |
| Prisma 7, PostgreSQL 18                         | миграции и типизированные запросы            |
| DataLoader                                      | пакетная загрузка вложенных полей            |
| Zod                                             | проверка переменных окружения и данных       |
| Docker, Docker Compose                          | образ и запуск вместе с базой                |
| Vitest, Testcontainers                          | unit- и e2e-тесты на настоящем PostgreSQL    |

## Запуск

Нужны только Docker и Docker Compose:

```bash
cp .env.example .env
docker compose up --build
```

Откройте http://localhost:3000 — корень перенаправит в Sandbox. Миграции и заполнение базы выполняются сами.

Без Docker нужен Node.js 26 (версия в `.nvmrc`):

```bash
cp .env.example .env
npm ci
docker compose up -d db     # только база
npm run db:setup            # миграции + данные
npm run start:dev
```

Проверки: `npm test`, `npm run test:e2e`, `npm run lint`, `npm run typecheck`.

## Пример запроса

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Полная схема — в [`schema.gql`](schema.gql). Она генерируется из кода и коммитится, а e2e-тест падает, если файл устарел: изменение публичного контракта видно в diff.

## Архитектурные решения

**Структура и разделение ответственности.** Каждый раздел визитки — отдельный модуль (`profile`, `skills`, `experience`, `projects`) с одинаковыми слоями: резолвер → загрузчик → сервис → репозиторий. Резолвер не знает о базе, Prisma вызывается только из репозиториев, бизнес-правила живут в сервисах — поэтому они тестируются без базы, а смена ORM затрагивает один слой. Дочерние модули добавляют поля в `Profile` своими резолверами, и новый раздел не требует правок существующих.

**Вложенные данные без N+1.** Вложенные поля грузятся через DataLoader: ключи всех родителей одного тика уходят в базу одним запросом с `IN (…)`. Загрузчики создаются заново на каждый запрос, поэтому кэш не пересекается между клиентами. E2e-тест считает SQL-запросы: визитка с 25 элементами в каждом списке выполняется тем же числом запросов, что и с одним.

**Взаимодействие с базой.** Схема описана в `prisma/schema.prisma`, доступ — через типизированный клиент Prisma. Правила целостности живут в самой базе (внешние ключи, уникальные индексы, CHECK на период работы), а не только в коде. Публичный контракт отделён от таблиц: GraphQL-модели объявлены отдельно, а enum'ы API сверяются с enum'ами базы на этапе компиляции, поэтому переименование в базе не может молча изменить API.

**Инициализация и заполнение.** При старте контейнера выполняются `prisma migrate deploy`, затем заполнение, затем запуск API — отдельных ручных шагов нет. Данные визитки — это код в [`profile.data.ts`](src/database/seed/data/profile.data.ts), который проверяется Zod-схемой до записи. Синхронизация идёт по естественным ключам в одной транзакции: повторный запуск безопасен, id записей стабильны, удалённое из файла удаляется из базы.

**Читаемость и поддерживаемость.** Строгий TypeScript, ESM, линтер с type-aware правилами и единое форматирование — всё проверяется в CI. Одинаковая структура модулей означает, что новый раздел пишется по образцу соседнего. Ошибки не теряются: намеренные получают стабильный код в `extensions`, неожиданные маскируются и уходят в лог с идентификатором запроса, так что клиент не видит ни SQL, ни стека.

**Корректная работа после запуска с нуля.** `docker compose up --build` на чистой машине поднимает базу и приложение и отдаёт визитку. Это же проверяет CI отдельной задачей: поднимает стек с нуля и запрашивает визитку по HTTP. Публичный эндпоинт защищён от злоупотреблений — лимит сложности запроса, ограничение размера тела и ограничение частоты запросов по IP.

## Тесты

- **unit** (`src/**/*.spec.ts`, 110 тестов): загрузчики, сервисы, валидация данных, маскирование ошибок, конфигурация.
- **e2e** (`test/`, 24 теста): PostgreSQL в Testcontainers с теми же миграциями и данными, что в production. Проверяются пример запроса, порядок данных, отсутствие N+1, ограничения базы, лимиты и актуальность `schema.gql`.

CI прогоняет всё перечисленное на каждый push и pull request.

## Деплой

Render собирает образ из `Dockerfile` по [`render.yaml`](render.yaml), база — отдельный проект Neon. Строка подключения задаётся в панели Render и в репозиторий не попадает. Миграции и заполнение выполняются при старте контейнера, отдельного шага деплоя нет.

## Обновление данных визитки

Отредактируйте [`profile.data.ts`](src/database/seed/data/profile.data.ts) и выполните `npm run db:seed` — или пересоберите контейнер. Изменённые записи обновятся, удалённые из файла исчезнут из базы.
